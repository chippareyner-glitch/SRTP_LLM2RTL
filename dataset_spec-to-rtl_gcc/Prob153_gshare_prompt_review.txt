I would like you to implement a module named TopModule with the following
interface. All input and output ports are one bit unless otherwise
specified.

 - input  clk
 - input  areset

 - input  predict_valid,
 - input  predict_pc (7 bits)
 - output predict_taken
 - output predict_history (7 bits)

 - input  train_valid
 - input  train_taken
 - input  train_mispredicted
 - input  train_history (7 bits)
 - input  train_pc (7 bits)

The module should implement a gshare branch predictor with 7-bit pc and
7-bit global history, hashed (using xor) into a 7-bit index. This index
accesses a 128-entry table of two-bit saturating counters. The branch
predictor should contain a 7-bit global branch history register. The
branch predictor has two sets of interfaces: One for doing predictions
and one for doing training. The prediction interface is used in the
processor's Fetch stage to ask the branch predictor for branch direction
predictions for the instructions being fetched. Once these branches
proceed down the pipeline and are executed, the true outcomes of the
branches become known. The branch predictor is then trained using the
actual branch direction outcomes.

When a branch prediction is requested (predict_valid = 1) for a given pc,
the branch predictor produces the predicted branch direction and state of
the branch history register used to make the prediction. The branch
history register is then updated (at the next positive clock edge) for
the predicted branch.

When training for a branch is requested (train_valid = 1), the branch
predictor is told the pc and branch history register value for the branch
that is being trained, as well as the actual branch outcome and whether
the branch was a misprediction (needing a pipeline flush). Update the
pattern history table (PHT) to train the branch predictor to predict this
branch more accurately next time. In addition, if the branch being
trained is mispredicted, also recover the branch history register to the
state immediately after the mispredicting branch completes execution.

If training for a misprediction and a prediction (for a different,
younger instruction) occurs in the same cycle, both operations will want
to modify the branch history register. When this happens, training takes
precedence, because the branch being predicted will be discarded anyway.
If training and prediction of the same PHT entry happen at the same time,
the prediction sees the PHT state before training because training only
modifies the PHT at the next positive clock edge. The following timing
diagram shows the timing when training and predicting PHT entry 0 at the
same time. The training request at cycle 4 changes the PHT entry state in
cycle 5, but the prediction request in cycle 4 outputs the PHT state at
cycle 4, without considering the effect of the training request in cycle
4. Reset is asynchronous active-high.

Assume all sequential logic is triggered on the positive edge of the
clock.

# Specification Analysis Report: GShare Branch Predictor

## 1. Specification Summary

The module implements a **gshare branch predictor** with:
- **7-bit PC** and **7-bit global history** register (GHR)
- **XOR-based hashing** to generate 7-bit index (128-entry PHT)
- **Two-bit saturating counters** in PHT (128 entries)
- **Dual interface**: prediction (fetch stage) and training (execution stage)
- **Priority handling**: training overrides prediction in conflict cases
- **Asynchronous reset** (active high)

## 2. Ambiguity Analysis

**Critical Ambiguities Identified:**

1. **GHR Update Timing for Predictions**: The spec states "branch history register is then updated (at the next positive clock edge)" but doesn't clarify if this happens immediately after prediction or if it's conditional on something else.

2. **Training Priority Logic**: "training takes precedence" is ambiguous about what exactly gets overridden - only GHR updates, or also PHT access conflicts?

3. **"Same PHT Entry" Definition**: Unclear if "same PHT entry" means identical index or identical PC/history combination.

4. **Reset State**: No specification of initial values for PHT counters and GHR after reset.

## 3. Missing Critical Details

**Essential Missing Specifications:**

1. **PHT Counter Update Policy**: How exactly should the 2-bit saturating counters be updated during training?
   - Increment/decrement rules for taken/not-taken
   - Saturation limits (typically 0-3 or 1-2?)

2. **GHR Recovery Mechanism**: How is GHR recovered for mispredictions?
   - Does train_history represent the state after the mispredicted branch?
   - How is this value applied to the GHR?

3. **Simultaneous Operation Handling**: Need explicit rules for:
   - Same-cycle predict and train on different entries
   - Same-cycle predict and train on same entry
   - Multiple operations in one cycle (spec doesn't forbid this)

4. **PHT Access Conflict Resolution**: When predict and train access same PHT entry simultaneously:
   - Read/write hazard handling
   - Bypass logic requirements

## 4. Edge Cases & Boundary Conditions

**Critical Edge Cases to Handle:**

1. **Reset During Operation**: Behavior when areset is asserted mid-operation
2. **Back-to-Back Mispredictions**: Handling multiple mispredictions in consecutive cycles
3. **Maximum Rate Scenarios**: All ports active every cycle
4. **Same PC, Different History**: Different branches with same PC but different global history
5. **Training Without Prediction**: Valid training for a branch that wasn't predicted
6. **Invalid Signal Combinations**: What if predict_valid and train_valid are both high for same PC?

## 5. Functional Correctness Prediction

**Potential Failure Points:**

1. **Timing Violations**: PHT read-modify-write hazards if not properly pipelined
2. **Priority Logic Errors**: Incorrect handling of predict/train conflicts
3. **GHR Corruption**: Improper state recovery during mispredictions
4. **Counter Overflow**: Incorrect saturation logic in PHT updates

**Verification Priorities:**
- Misprediction recovery sequence
- Simultaneous predict/train scenarios
- Reset initialization and recovery
- PHT update correctness
